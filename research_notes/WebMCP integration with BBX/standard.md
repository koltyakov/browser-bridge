# Browser WebMCP proposal and implementation

Research cutoff and retrieval date: October 9, 2026. These notes distinguish the published draft, Chrome implementation documentation, and integration inferences. No browser experiment was run, no software installed, and no source code changed. GitHub `main` and tip-of-tree protocol URLs are mutable; their contents were read on the cutoff date.

## What is WebMCP, and what are its native APIs?

### Takeaway

WebMCP is a proposed browser API for websites to register callable client-side tools for agents. The current API is `document.modelContext`, not the `navigator.modelContext` shown in earlier articles. It is not MCP's JSON-RPC transport implemented inside a browser, and it is not yet a W3C Standard.

### Cited findings

- Verified standards status: the specification retrieved on October 9 identifies itself as a **Draft Community Group Report, 9 October 2026**, published by the W3C Web Machine Learning Community Group. Its status explicitly says it is neither a W3C Standard nor on the W3C Standards Track. Editors include Microsoft and Google representatives. [Draft specification](https://webmachinelearning.github.io/webmcp/)
- Verified purpose: websites expose existing application functionality through JavaScript tools with natural-language descriptions and structured input schemas. Execution runs site-owned code in the page, can update visible UI, and can reuse the existing session and application state. The explainer first appeared August 13, 2025. [Proposal README, retrieved October 9, 2026](https://github.com/webmachinelearning/webmcp)
- Draft API: `Document.modelContext` is marked `SecureContext` and `SameObject`. `ModelContext` extends `EventTarget`, is exposed to `Window`, and currently defines `registerTool(tool, options)`, `getTools(options)`, and `executeTool(registeredTool, inputObject, options)`. All three return promises. This draft does not expose `ModelContext` to workers. [Draft API and IDL, October 9, 2026](https://webmachinelearning.github.io/webmcp/#api)
- Verified current Chrome documentation uses `document.modelContext` throughout. The imperative documentation was published May 18 and updated September 21, 2026. The current proposal also uses `document.modelContext`. Treat earlier `navigator.modelContext` and `navigator.modelContextTesting` code as version-specific, not the current normative API. [Chrome imperative API](https://developer.chrome.com/docs/ai/webmcp/imperative-api); [current proposal](https://github.com/webmachinelearning/webmcp)
- Draft registration: tool definitions require `name`, `description`, and an `execute` callback; `title`, `inputSchema`, and `annotations` are optional in the draft IDL. Chrome's introductory documentation says an input schema is required, so the draft and prose documentation are not perfectly aligned. `registerTool` supports an `AbortSignal` to unregister a tool and `exposedTo` to share it with named secure origins. Unregistration is separate from cancellation of an invocation already running. [Draft tool dictionary](https://webmachinelearning.github.io/webmcp/#model-context-tool); [Chrome imperative API, September 21, 2026](https://developer.chrome.com/docs/ai/webmcp/imperative-api)
- Chrome documents optional annotation hints `readOnlyHint`, `untrustedContentHint`, `consequentialHint`, and `debugging`. The last is documented as available from Chrome 156. These describe intended behavior, not enforceable proof that a tool is safe or truthful. [Chrome imperative API, September 21, 2026](https://developer.chrome.com/docs/ai/webmcp/imperative-api); [example extension trust boundary, retrieved October 9](https://github.com/GoogleChromeLabs/webmcp-extension/)
- Verified implementation/proposal distinction: Chrome documents both imperative JavaScript and declarative HTML forms. The proposal README explicitly says the declarative counterpart remains a separate exploration and is **not part of the specification at this time**. Do not present every Chrome declarative feature as an agreed W3C draft requirement. [Chrome overview, updated October 7, 2026](https://developer.chrome.com/docs/ai/webmcp); [proposal's declarative status](https://github.com/webmachinelearning/webmcp#future-exploration-declarative-api)
- Chrome's declarative implementation uses `<form toolname="..." tooldescription="...">`. The browser derives tool parameters from form controls and generates an input schema. `toolparamdescription` supplies a parameter description; labels and `aria-description` provide fallback descriptions. Removing `toolname` or `tooldescription` unregisters the tool. [Chrome declarative API, published May 18, updated September 25, 2026](https://developer.chrome.com/docs/ai/webmcp/declarative-api)
- Declarative execution fills and focuses the form. Submission defaults to a user clicking Submit; `toolautosubmit` permits automatic submission. Chrome documents `SubmitEvent.agentInvoked`, and `respondWith(...)` after `preventDefault()` to supply a result. `toolactivated` and `toolcancel` occur on `document.modelContext`; the earlier `window.ontoolactivated` and `window.ontoolcancel` are documented as unsupported from Chrome 156. `:tool-form-active` and `:tool-submit-active` provide visible focus styling. [Chrome declarative API, September 25, 2026](https://developer.chrome.com/docs/ai/webmcp/declarative-api)
- Verified distinction from backend MCP: the specification does not prescribe the format in which a browser exposes tools to its agent. A browser can use MCP, proprietary function calling, or another representation. MCP vocabulary does not imply a built-in MCP network server, `tools/list` endpoint, or universal remote discovery protocol. [Draft interaction with agents](https://webmachinelearning.github.io/webmcp/#interaction-with-agents)
- Same-name projects: the official proposal lists the independent open-source **WebMCP / MCP-B** implementation as prior art, and acknowledges implementations by Alex Nahas and Jason McGhee. A package or GitHub organization with "WebMCP" in its name is not automatically the W3C proposal or a native browser implementation. The `WebMCP-org/chrome-devtools-quickstart` README, for example, imports `@mcp-b/global` to add `navigator.modelContext`; that is evidence of library-provided behavior, not evidence that a browser ships that native API. [Official prior art](https://github.com/webmachinelearning/webmcp#prior-art); [independent quickstart](https://github.com/WebMCP-org/chrome-devtools-quickstart)

### Inferences

- A BBX integration should label native support and library/polyfill support separately. Checking a property name alone cannot establish that its implementation is browser-native. Current integrations should start with `document.modelContext` and explicitly version any legacy compatibility behavior. This follows from the current draft and the library quickstart's own injected API. [Draft](https://webmachinelearning.github.io/webmcp/#api); [library quickstart](https://github.com/WebMCP-org/chrome-devtools-quickstart)
- WebMCP complements DOM, accessibility, screenshots, and input simulation; it does not replace them for pages without tools or actions not covered by tools. The proposal explicitly permits fallback browser automation. [Proposal existing actuation techniques](https://github.com/webmachinelearning/webmcp#existing-web-actuation-techniques)

### Gaps

- The precise milestone for the `navigator` to `document` move was not established. The current shape is clear, but an implementation must test actual browser versions rather than infer compatibility from the name.
- Chrome prose and draft IDL differ on required input schemas, and explanatory examples do not always distinguish a raw callback result from the serialized `executeTool` result. Use the target build and its versioned protocol as implementation authority.

## How can extensions and agents discover and execute tools?

### Takeaway

The current public JavaScript API includes discovery and execution, and Chrome explicitly permits extension content scripts to use it. Chromium also has an experimental CDP `WebMCP` domain for event-based discovery, invocation, cancellation, and result observation. These are distinct access paths, not a standardized external MCP transport.

### Cited findings

- Public JS discovery: `await document.modelContext.getTools()` returns authorized tools. Descriptors include the name, description, input schema, annotations, origin, and owning `window`. Same-origin documents within the frame tree are included by default. Cross-origin discovery requires explicit `fromOrigins`, and the tool owner must expose the tool to the caller's origin through `exposedTo`. [Chrome imperative API, September 21, 2026](https://developer.chrome.com/docs/ai/webmcp/imperative-api); [draft discovery](https://webmachinelearning.github.io/webmcp/#dom-modelcontext-gettools)
- Invocation: pass a discovered `RegisteredTool` and a JSON-serializable object to `executeTool`. An execution `AbortSignal` supports cancellation; the page's `execute(input, {signal})` callback can propagate it to network or asynchronous work. Chrome documents JSON-stringified arguments as deprecated from Chrome 155. [Chrome imperative API, September 21, 2026](https://developer.chrome.com/docs/ai/webmcp/imperative-api)
- Draft result semantics: `executeTool` resolves to a stringified result, with `Promise<DOMString>` in the IDL. The draft defines failures including `NotFoundError`, `DataError`, `OperationError`, and unload-related `AbortError`. Chrome documentation also says execution returns null when navigation is triggered. These differences matter to result normalization and navigation handling. [Draft API](https://webmachinelearning.github.io/webmcp/#api); [draft execution errors](https://webmachinelearning.github.io/webmcp/#tool-execution-error); [Chrome imperative execution](https://developer.chrome.com/docs/ai/webmcp/imperative-api#execute_tool)
- Dynamic discovery: `toolchange` notifies consumers about registration/unregistration. The current proposal does not define `updateTool`, disabled tool groups, lazy schemas, or an `outputSchema` contract; these remain discussions. [Chrome imperative events](https://developer.chrome.com/docs/ai/webmcp/imperative-api#events); [proposal best practices and open questions, retrieved October 9](https://github.com/webmachinelearning/webmcp)
- Verified extension access: Chrome's overview expressly cautions that extensions can query and execute WebMCP tools with content scripts. GoogleChromeLabs' example extension calls `document.modelContext.getTools()` and `executeTool()` directly from its content script and relays descriptors/results with `chrome.runtime` messaging. It listens for tool changes and maps owner windows to extension frame IDs. [Chrome overview, October 7, 2026](https://developer.chrome.com/docs/ai/webmcp#imitate_an_agent_to_test_your_tools); [example `extension/content.ts`, retrieved October 9](https://raw.githubusercontent.com/GoogleChromeLabs/webmcp-extension/main/extension/content.ts)
- Verified compatibility problem: that example content script includes a fallback to stringified input arguments for older Chrome builds and a fallback between model-context events and old window events. These are explicit compatibility shims, not the preferred draft API. [Example content script, retrieved October 9](https://raw.githubusercontent.com/GoogleChromeLabs/webmcp-extension/main/extension/content.ts)
- Browser agents are not limited to the public in-page discovery rules. The draft says the browser's agent uses a different internal mechanism to retrieve exposed tools, and does not prescribe the agent-facing format. Thus an extension using public JS should not assume it automatically receives the same privileges as a built-in browser agent. [Draft `getTools` description](https://webmachinelearning.github.io/webmcp/#model-context-container); [agent integration](https://webmachinelearning.github.io/webmcp/#interaction-with-agents)
- Verified tip-of-tree CDP definition: `experimental domain WebMCP` defines `enable`, `disable`, `invokeTool`, and `cancelInvocation`. Enabling produces a `toolsAdded` event for all current registrations. Subsequent `toolsAdded` and `toolsRemoved` events track changes. There is no `getTools` or `listTools` command in this retrieved domain definition. [Chromium CDP source, retrieved October 9, 2026](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/WebMCP.pdl)
- CDP `invokeTool` takes `frameId`, `toolName`, and an `input` object and immediately returns `invocationId`, before tool events. `toolInvoked` records execution; `toolResponded` returns status `Completed`, `Canceled`, or `Error`, optional output, and error information. `cancelInvocation` targets an invocation ID. Tool descriptors include `frameId`, input schema, annotations, optional declarative backend-node ID, and optional registration stack trace. CDP annotation names are `readOnly`, `untrustedContent`, `consequential`, `debugging`, and `autosubmit`, unlike the JS `*Hint` names. [CDP source, retrieved October 9](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/WebMCP.pdl)
- Security fact: the CDP source explicitly marks tool output as untrusted and a prompt-injection risk. The example extension also states that annotations are page-provided hints, not guarantees, and that its deliberate choice to trust them is not a production-ready security policy. [CDP source](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/WebMCP.pdl); [example extension trust boundary](https://github.com/GoogleChromeLabs/webmcp-extension/)

### Inferences

- BBX can plausibly relay the public API through an extension content script, or use its existing debugger/CDP path. A CDP implementation needs to retain `toolsAdded` events and await `toolResponded`; a one-shot invoke request is not the final tool result. This is an integration inference from the official extension and protocol source, not a verified statement about BBX's current code. [Example content script](https://raw.githubusercontent.com/GoogleChromeLabs/webmcp-extension/main/extension/content.ts); [CDP source](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/WebMCP.pdl)
- Tool identities should include tab/document/frame context, not only the tool name. Native descriptors contain an owner window, CDP descriptors contain a frame ID, and tool names are unique within a model context rather than globally. Navigation and re-registration can invalidate prior discovery. [Draft tool definition](https://webmachinelearning.github.io/webmcp/#tool-definition); [CDP source](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/WebMCP.pdl)
- Preserve independent user authorization for consequential operations, regardless of `readOnlyHint`. Neither schemas nor annotations prove implementation behavior. [Example extension security warning](https://github.com/GoogleChromeLabs/webmcp-extension/#trust-boundary); [draft security](https://webmachinelearning.github.io/webmcp/#security-privacy)

### Gaps

- Tip-of-tree CDP establishes that the protocol exists, not the first released Chrome milestone containing every method. No live Chrome was queried to verify domain availability or extension-world behavior on the user's build.
- The exact limits of content-script privileges across denied permissions policy, absent host permissions, and cross-origin frame injection were not tested. The sample demonstrates an access pattern, not a license to bypass those controls.
- The official example handles navigation results with JSON-LD reads and frame/tab logic, but a general standardized cross-document continuation contract remains unresolved in the proposal.

## What is available as of October 9, 2026, and what remains experimental?

### Takeaway

Chrome and Edge have verified experimental availability through origin trials, not verified unconditional default-on shipping. Mozilla is neutral; WebKit opposes the proposal. The official project also lists other agent integrations, but that does not establish interoperable engine support or full API parity.

### Cited findings

- Timeline: Chrome announced an early preview on February 10, 2026. Its June 9 origin-trial announcement says WebMCP is available in Chrome 149 and explicitly describes origin trials as time-limited experimental access. The overview updated October 7 still labels the API an origin trial and offers the `chrome://flags/#enable-webmcp-testing` local-development flag. [February preview](https://developer.chrome.com/blog/webmcp-epp); [June origin-trial announcement](https://developer.chrome.com/blog/ai-webmcp-origin-trial); [October overview](https://developer.chrome.com/docs/ai/webmcp)
- Chrome Status, last updated September 28, 2026, records experimental milestones 146 for desktop/Android and an origin-trial start of 149 for desktop/Android/WebView. Original trial last milestones are 156. An extension request created September 28 targets desktop last milestone 162 and says feedback prompted API improvements. These are experiment/request records, not stable shipping dates or confirmation that every requested extension was approved. [Chrome Status machine-readable record, retrieved October 9](https://chromestatus.com/api/v0/features/5117755740913664)
- Important inconsistent tracker fields: the same Chrome Status record says `is_released: false`, Chrome status "Proposed", and no shipped milestone. It also contains `shipping_year: 2026` and a rollout-plan label "Will ship enabled for all users". Those planning fields do not override the trial docs or prove a launch. Its Firefox/Safari "No signal" entries are stale relative to their own standards-position repositories. [Chrome Status record](https://chromestatus.com/api/v0/features/5117755740913664); [Mozilla position](https://github.com/mozilla/standards-positions/issues/1412); [WebKit position](https://github.com/WebKit/standards-positions/issues/670)
- Official proposal implementation-status document lists Chrome origin trial 149 and Edge origin trial 150. For Edge it points to Microsoft's trial and refers to Chrome's platform implementation status. This is verified project-maintainer reporting, not a claim of default-on support in all Chromium derivatives. [Implementation status, retrieved October 9](https://raw.githubusercontent.com/webmachinelearning/webmcp/main/implementation-status.md); [linked Microsoft Edge trial](https://developer.microsoft.com/en-us/microsoft-edge/origin-trials/trials/0b76fe60-b266-458e-a285-04e375c0c31a)
- Mozilla adopted a neutral position, labelled August 3, 2026 and closed as completed August 5. Its June 1 analysis identifies potential value but unresolved adversarial, naming, openness, and interoperability concerns. August discussion mentions interest in imperative function-call mechanisms, but is not an implementation announcement or a switch to a positive position. [Mozilla standards position issue 1412](https://github.com/mozilla/standards-positions/issues/1412)
- WebKit's June 3 position opposes the proposal, finalized June 11. Its stated concerns include a separate agent-facing layer, unverifiable descriptions, site detection of agent use, security/privacy, consent, interoperability, and standards venue. June 17 follow-up calls for problem-definition and broader standards discussion rather than iterating within the current architecture. This is opposition, not "no signal". [WebKit standards position issue 670](https://github.com/WebKit/standards-positions/issues/670)
- Other project-listed integrations: Brave Leo support is labelled experimental; ChatGPT Desktop is labelled supported without version or details; Meta Ray-Ban Display web-app integration is labelled coming soon, off by default and enabled per device. These claims are present in the official proposal repository, but were not independently checked against each product or tested for API parity. [Implementation status, retrieved October 9](https://raw.githubusercontent.com/webmachinelearning/webmcp/main/implementation-status.md)
- Runtime limits: tools are discovered by visiting the site, not through a global catalog. Chrome says the API is primarily for local browser workflows with a human in the loop, although headless use may be possible. The official example actually runs headless extension smoke tests, so "headless is impossible" would be too strong. Neither source makes WebMCP a server-only service API. [Chrome limitations, October 7](https://developer.chrome.com/docs/ai/webmcp#limitations); [example extension testing](https://github.com/GoogleChromeLabs/webmcp-extension/#run-the-test-suite)
- Origin controls: the `tools` permissions policy defaults to `self`, allowing top-level and same-origin contexts but not cross-origin iframes without delegation. `allow="tools"` enables a cross-origin frame to use the API; public cross-origin sharing additionally needs `exposedTo` and matching `fromOrigins`. A `Permissions-Policy: tools=()` header can disable the API. [Chrome permissions policy](https://developer.chrome.com/docs/ai/webmcp#permissions_policy); [imperative cross-origin controls](https://developer.chrome.com/docs/ai/webmcp/imperative-api#cross-origin_iframes); [draft mitigation](https://webmachinelearning.github.io/webmcp/#mitigation-disable-permissions-policy)
- Remaining proposal work includes output schemas, multimodal/transferable/streamed data, progress reporting, confirmation/elicitation, cross-document responses, and background service-worker tools. The README describes service-worker registration/discovery as an extension being explored separately, not the current `Window` API. [Proposal open questions, retrieved October 9](https://github.com/webmachinelearning/webmcp#open-questions); [draft IDL](https://webmachinelearning.github.io/webmcp/#idl-index)
- Core safety limit: tool metadata, descriptions, implementation behavior, and returned content can disagree or be malicious. The specification discusses tool poisoning, output injection, over-parameterization/privacy leakage, and misrepresentation of intent. Structured schemas improve interface clarity but do not eliminate prompt injection or establish user consent. [Draft security and privacy, October 9, 2026](https://webmachinelearning.github.io/webmcp/#security-privacy)

### Inferences

- For BBX, WebMCP should be optional and capability-detected, with ordinary browser inspection/input retained. The strongest available evidence is an experimental Chromium-family implementation, not cross-engine standardization. [Chrome overview](https://developer.chrome.com/docs/ai/webmcp); [Mozilla position](https://github.com/mozilla/standards-positions/issues/1412); [WebKit position](https://github.com/WebKit/standards-positions/issues/670)
- Feature detection, protocol availability, and per-origin trial activation need separate checks. A Chrome version number alone does not demonstrate that an arbitrary visited page can register tools. [Chrome trial and local flag requirements](https://developer.chrome.com/docs/ai/webmcp#get_started)

### Gaps

- No verified unconditional stable shipping date or cross-browser baseline date. Do not turn Chrome Status's planning fields or future trial-end milestones into a release promise.
- No independent verification of current Firefox implementation progress, Safari technical implementation, ChatGPT Desktop's exact integration, Brave's release channel, or Meta rollout scope.
- Origin-trial expiry/extension approval was not independently confirmed in the trial console. Report Chrome 149 trial availability and the September extension request separately.
- These notes establish documented capability, not a tested BBX implementation, benchmark, or measured reliability improvement.
