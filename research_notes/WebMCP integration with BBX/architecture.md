# WebMCP integration with BBX architecture

Research date: October 9, 2026. Repository inspected at commit `08ace5826301fcdf59ea57b042f85aca930de036`, package version 1.12.2. This is a source review, not a browser compatibility test. No application code, tests, browser state, or packages were changed. Repository citations below point to the inspected commit. [Repository package](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/package.json)

## Can BBX consume WebMCP directly, or only through a testing API?

### Takeaway

Yes. The current Chrome documentation explicitly supports extension consumers using `document.modelContext.getTools()` and `document.modelContext.executeTool()`, including ordinary content scripts. Do not design the integration around the older `navigator.modelContextTesting.listTools()` API. The API is still experimental and version-sensitive. [Chrome imperative API](https://developer.chrome.com/docs/ai/webmcp/imperative-api); [Chrome overview](https://developer.chrome.com/docs/ai/webmcp)

### Cited Findings

- Chrome's imperative API documentation, updated September 21, 2026, exposes registration and consumption on `document.modelContext`. `getTools()` is asynchronous and returns tool descriptors with name, description, inputSchema, annotations, origin, title, and a `window` object. `executeTool(tool, inputArgs, options)` consumes a discovered descriptor, takes JSON-serializable object arguments, and supports an AbortSignal. It returns a result or `null` when navigation is triggered. JSON-stringified arguments are deprecated from Chrome 155. [Official imperative API](https://developer.chrome.com/docs/ai/webmcp/imperative-api)
- Google's example extension accesses `document.modelContext` directly in a content script. It lists descriptors, removes nonserializable Window objects from outgoing messages, finds a tool by name and owning Window for execution, and calls `executeTool`. The example contains an older-build fallback for stringified arguments after a parse error. This is actual consumer source, not a speculative API description. [Example content script](https://github.com/GoogleChromeLabs/webmcp-extension/blob/main/extension/content.ts)
- Chrome's overview, updated October 7, 2026, explicitly says extensions can query and execute tools with content scripts. Its security guidance says host permissions are required. BBX already declares `scripting`, `debugger`, `tabs`, and `<all_urls>` host access, although user-enabled-window controls restrict actual bridge operations. [Chrome overview](https://developer.chrome.com/docs/ai/webmcp); [Agent security](https://developer.chrome.com/docs/agents/security); [BBX manifest](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/manifest.json#L13-L27); [BBX window-scoped resolver](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-page.js#L168-L260)
- Chrome offers an origin trial from Chrome 149 and the local `#enable-webmcp-testing` flag. Google's example extension separately requires Chrome 150+ and the flag. These are different requirements, not evidence of universal stable availability. BBX's minimum supported Chrome version is 114, so WebMCP must be optional rather than a new baseline requirement. [Chrome overview](https://developer.chrome.com/docs/ai/webmcp); [Example requirements](https://github.com/GoogleChromeLabs/webmcp-extension#requirements); [BBX manifest](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/manifest.json#L1-L6)
- Discovery defaults to tools from the calling document and same-origin documents in the frame tree. Cross-origin discovery requires explicit `fromOrigins` plus tool exposure to the calling origin. Cross-origin registration requires delegated `tools` Permissions Policy, for example `allow="tools"`; registration can provide `exposedTo`. These browser rules should not be confused with BBX's own profile/window authorization. [Official discovery and iframe rules](https://developer.chrome.com/docs/ai/webmcp/imperative-api)
- Registered tools can appear and disappear. Consumers can listen to `toolchange`. Declarative form tools can navigate, target an iframe, or open a new tab; the example extension has special handling for navigation results and JSON-LD in the destination document. [Official API events](https://developer.chrome.com/docs/ai/webmcp/imperative-api); [Example consumer source](https://github.com/GoogleChromeLabs/webmcp-extension/blob/main/extension/content.ts)
- Annotations currently include `readOnlyHint`, `untrustedContentHint`, and `consequentialHint`; `debugging` is documented as available from Chrome 156. These are page-provided hints, not guarantees. Google's example deliberately trusts them for demonstration and explicitly says it is not production-ready. [Official annotations](https://developer.chrome.com/docs/ai/webmcp/imperative-api); [Example trust boundary](https://github.com/GoogleChromeLabs/webmcp-extension#trust-boundary)

### Inferences

- The preferred adapter should use the direct consumer API from BBX's isolated-world content script. A MAIN-world/CDP route is useful for a proof of concept or an explicitly supported compatibility backend, but current evidence does not require either for the main implementation. [Official extension example](https://github.com/GoogleChromeLabs/webmcp-extension/blob/main/extension/content.ts)
- Feature-detect `document.modelContext`, `getTools`, and `executeTool` in the target document. Return a clear supported/unsupported result. Distinguish an unavailable API from an available API with zero registered tools. Do not auto-enable flags, register replacement tools on behalf of arbitrary sites, or raise BBX's Chrome baseline for every user. [Experimental availability](https://developer.chrome.com/docs/ai/webmcp); [Current BBX baseline](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/manifest.json)
- If old-build compatibility is important, add a separately named/internal legacy adapter only after testing its exact signatures on those builds. Do not silently reinterpret older `navigator.modelContextTesting` examples as the current standard. The direct API now has documented discovery and execution methods. [Current primary documentation](https://developer.chrome.com/docs/ai/webmcp/imperative-api)

### Gaps

- No live Chrome test was permitted. Availability in the user's installed browser, enabled flags, origin trials, isolated-world API exposure in that particular build, cancellation behavior, and declarative navigation behavior remain unverified.
- I did not establish the precise historical Chrome version where `navigator.modelContextTesting` was replaced, or a supported compatibility range for it. Current official documentation and current Google example source are sufficient to reject a testing-only architecture, but not to promise old-browser support.

## Which integration pieces does BBX already have?

### Takeaway

BBX already has the native-messaging transport, multi-profile and remote routing, enabled-window scope, content-script injection, MAIN-world scripting, CDP evaluation, and a generic MCP dispatcher. It does not currently have a WebMCP method family, typed tool discovery, retained WebMCP descriptors, stale-tool validation, or a WebMCP-specific execution policy. [Architecture guide](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/AGENTS.md); [Current registry](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/protocol/src/registry.js)

### Cited Findings

- Requests flow through MCP or the `bbx` CLI, BridgeClient, the local daemon, native messaging, the extension background worker, and content scripts or CDP. Responses return as shared success/failure envelopes. No new server transport is needed to carry a JSON WebMCP descriptor or invocation result. [AGENTS data flow](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/AGENTS.md#L7-L35)
- `packages/protocol/src/registry.js` is the canonical registry for method groups, tab routing, exposed parameters, capability metadata, complexity, and debugger policy. `BridgeMethod` is a closed TypeScript union in `packages/protocol/src/types.ts`. `validateBridgeRequest` rejects unsupported methods and normalizes registered method parameters. Adding a WebMCP family requires shared protocol changes; sending an unregistered `webmcp.*` string will not work today. [Registry](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/protocol/src/registry.js#L91-L102); [Types](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/protocol/src/types.ts#L65-L143); [Validation](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/protocol/src/protocol.js#L377-L454)
- Existing `page.evaluate` uses CDP `Runtime.evaluate` in the page's main context, with `awaitPromise`, a normalized timeout, `returnByValue: true`, and `userGesture: true`. `returnByValue: false` is explicitly rejected because BBX cannot consume remote CDP objects. There is no public arbitrary `cdp.send` bridge method; the CDP family exposes selected commands. [Evaluation implementation](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-evaluate.js); [Evaluation normalization](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/protocol/src/protocol.js#L1393-L1417); [Selected CDP commands](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-page.js#L944-L1033)
- BBX also already uses `chrome.scripting.executeScript({world:'MAIN'})` for navigation and console/network instrumentation. Content scripts load as ordered classic scripts, are injected on demand, and communicate through `bridge.execute`. Main-frame messages explicitly target frame 0. The frame helper supports child-frame messages and bounded frame discovery, with a three-second cache and a twelve-frame cap. These are reusable mechanics, not a WebMCP implementation. [Injection and MAIN-world hooks](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-content-script.js#L13-L22); [MAIN-world and frame messaging](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-content-script.js#L102-L289); [Content dispatch](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/content-script.js#L136-L210)
- The daemon selects a connected extension using browser/profile/connection selectors. Multiple matching profiles return `TAB_MISMATCH` with `ambiguous_browser_target`; a tab ID alone does not select a profile. MCP carries `extensionId`, `targetBrowser`, `targetProfile`, and `destinationId` through existing routing. Connection IDs change on reconnect. [Daemon routing](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/native-host/src/daemon.js#L1281-L1383); [MCP target schemas](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/server.js#L60-L93); [MCP request target scope](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/handlers-utils.js#L59-L76)
- `resolveRequestTarget` enforces the enabled window, rejects tabs outside it, and uses a sticky working tab per agent session. It does not silently switch to the user's active tab when a working tab closes. Restricted URLs are rejected for scriptable operations. Enabled-window state is session-scoped and disabling/removing windows clears bridge state. [Target resolver](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-page.js#L159-L260); [URL and window checks](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-routing.js); [Window lifecycle](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-window-session.js)
- Capability names and registry mappings remain compatibility metadata, not a fine-grained WebMCP consent system. `capabilities.js` calls them legacy buckets and refers to former capability gates. The inspected dispatcher and target resolver enforce window/tab scope, not per-page-tool authorization. Do not present these mappings as an existing purchase/delete approval mechanism. [Capability helper](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/protocol/src/capabilities.js#L54-L64); [Current dispatch](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background.js#L887-L1009); [Target resolver](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-page.js#L168-L260)
- `browser_call` accepts a registered method plus generic parameter object, routes it through the shared protocol, and returns structured evidence. `protocol.describe` provides cheap method/group discovery. Modern MCP exposes a fixed compact tool list; BBX's code deliberately avoids changing it as a side effect of requests. Legacy typed tools can be enabled by exact name, but these are predeclared BBX tools, not arbitrary site tools. [Raw MCP handler](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/handlers-page.js#L508-L552); [Toolset design](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/toolset.js); [Protocol description](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/protocol/src/registry.js#L952-L996)
- Batch execution uses an explicit read-only allowlist. MCP retries use a separate safe-method allowlist; `page.evaluate` is not in either. A WebMCP execution must not become batch-safe or retry-safe merely because a page claims `readOnlyHint:true`. [Batch policy](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/protocol/src/registry.js#L843-L905); [Retry policy](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/handlers-utils.js#L196-L251)
- Responses already have token-cost metadata and budgets. Native messages are limited to 1,048,576 bytes, and the extension leaves response headroom. Generic token enforcement recursively shrinks payloads and can return a continuation result; generic MCP evidence bounding caps strings, depth, entries, and total characters. These defaults can corrupt a tool schema or structured result if applied unchanged. Existing HAR and exact-sensitive-value methods demonstrate atomic-result exceptions. [Transport/default limits](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/protocol/src/defaults.js#L34-L41); [Token enforcement](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-helpers.js#L348-L447); [Response enrichment](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-action-log.js#L532-L665); [MCP evidence bounding](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/handlers-utils.js#L478-L530)
- MCP cancellation currently closes/disposes request-owned client work. That is not evidence of an end-to-end AbortSignal delivered to a page callback. The shared timeout function controls browser-operation deadlines for known methods; a new execution method should join it. [MCP cancellation](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/handlers-utils.js#L100-L164); [Client disposal](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/handlers-utils.js#L385-L415); [Operation deadlines](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/protocol/src/protocol.js#L666-L693)
- Existing evaluation tests verify forwarded CDP parameters, invalid input, and exceptions. Routing, frames, window access, dispatch, budgets, and MCP lifecycle have dedicated TypeScript test files. There are no WebMCP entries in the current method registry. Project rules require Node's built-in test runner, complete JS JSDoc with `// @ts-check`, reusable types in TypeScript, and no new `any`. [Evaluation tests](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/test/background-evaluate.test.ts); [Test directory](https://github.com/koltyakov/browser-bridge/tree/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/test); [Working/type rules](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/AGENTS.md#L128-L161)

### Inferences

- A zero-source-change development experiment is feasible through existing `page.evaluate`: await `document.modelContext.getTools()`, serialize only descriptor metadata, then resolve and execute one tool inside a subsequent expression. Never return descriptors wholesale because they contain Window objects, and never rely on a CDP remote-object ID because BBX explicitly disallows that result mode. This would be an experiment, not existing first-class WebMCP support. [Current evaluator](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-evaluate.js); [Direct consumer API](https://developer.chrome.com/docs/ai/webmcp/imperative-api)
- Keep the daemon and native host as generic carriers for the first adapter. They need tests for routing/deadlines, not a website-specific transport or an independent MCP server per tab. [Existing data flow](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/AGENTS.md#L7-L35)

### Gaps

- Source inspection does not establish behavior of the existing evaluator against actual WebMCP-enabled Chrome, origin-trial restrictions, or how long a pending tool callback survives document replacement.
- Existing BBX enabled-window consent is broader than action-level consent. A deterministic high-stakes approval policy would be new work, not a capability this repository already guarantees.

## What is the smallest generic integration, and what must it protect?

### Takeaway

Start with an optional, top-document-only adapter exposed through existing `browser_call` and `bbx call`. Two methods are the literal minimum, list and execute. I recommend three, `webmcp.list_tools`, `webmcp.get_tool`, and `webmcp.execute_tool`, so normal discovery stays compact and full schemas remain intact. All method names and contracts below are proposals, not shipped functionality. [BBX generic-protocol rule](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/AGENTS.md#L135-L140); [Existing generic dispatcher](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/handlers-page.js#L508-L552)

### Cited Findings

- The current browser consumer API returns descriptors and executes a descriptor, not simply a globally unique name. Default discovery includes same-origin frames; therefore a name alone is not a sufficient durable routing key. BBX's default content message already targets frame 0. [Official descriptor shape](https://developer.chrome.com/docs/ai/webmcp/imperative-api); [Frame-zero messaging](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-content-script.js#L178-L198)
- Tool metadata and output can carry prompt injections. Chrome recommends deterministic token limits, origin restrictions, user confirmation, and treatment of outputs as untrusted data. The example warns that a harmful page can mark a tool read-only or label its output trusted. [Official agent security](https://developer.chrome.com/docs/agents/security); [Example caveat](https://github.com/GoogleChromeLabs/webmcp-extension#trust-boundary)
- A WebMCP call can run with the user's authenticated browser session. A read-only tool can still reveal private information. Host permissions allow extensions to manipulate the page independently of WebMCP, so WebMCP does not itself narrow BBX's extension privileges. [Agent security](https://developer.chrome.com/docs/agents/security); [Tool security](https://developer.chrome.com/docs/ai/webmcp/secure-tools)
- BBX has a model for preserving atomic structured output in `network.export_har` and explicit sensitive-value reads. It also redacts persisted `page.evaluate` and `sensitive.read` diagnostics, while ordinary action summaries can include result-derived information. Both patterns matter for WebMCP. [HAR result handler](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/handlers-page.js#L554-L599); [Sensitive action logging](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-action-log.js#L322-L428)

### Inferences

#### Proposed generic contract

- `webmcp.list_tools` takes bounded discovery options such as `limit` and a continuation cursor. It returns `supported`, detected backend/API flavor, document identity, catalog revision, scope, total/returned counts, truncation metadata, and compact entries with `toolRef`, exact name, origin, bounded description, annotations, and schema availability. If exposing top-document tools only, explicitly filter descriptors with `tool.window === window`; otherwise a default `getTools()` call also exposes same-origin-frame tools. Do not silently imply all frames were searched. [Descriptor and discovery semantics](https://developer.chrome.com/docs/ai/webmcp/imperative-api)
- `webmcp.get_tool` takes `toolRef` and returns one exact descriptor's full input schema plus relevant metadata. Return an explicit too-large response if the schema exceeds bounds. Never hand the agent a recursively shortened schema as though it were authoritative. If retaining only two methods, `list_tools` can accept an exact-tool filter and full-schema mode, but that is a less clear contract. [Existing output shrinking](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-helpers.js#L348-L447); [Descriptor schema](https://developer.chrome.com/docs/ai/webmcp/imperative-api)
- `webmcp.execute_tool` takes `toolRef`, JSON object arguments, a bounded timeout, and any required explicit approval token under the chosen policy. It returns execution outcome, result or navigation indication, provenance/origin, document identity, and output-limit status. Use the current discovered browser descriptor internally, not a function supplied by the page over JSON and not JavaScript source interpolated from a tool name. Keep arguments as data. [Consumer execution](https://developer.chrome.com/docs/ai/webmcp/imperative-api); [Example value-based name lookup](https://github.com/GoogleChromeLabs/webmcp-extension/blob/main/extension/content.ts)
- An MCP agent calls these through fixed `browser_call` names. For example, first use `protocol.describe` with group `webmcp`, then `webmcp.list_tools`, `webmcp.get_tool`, and `webmcp.execute_tool` using the same destination/profile/tab selectors. Site tools remain descriptors in tool results; do not dynamically register each site-provided name in MCP `tools/list`. This works with both current BBX MCP eras and avoids arbitrary page metadata becoming trusted MCP server tool definitions. [Current static MCP policy](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/toolset.js); [Generic handler](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/handlers-page.js#L508-L552)

#### Scope, lifecycle, and security requirements

- Run normal `resolveRequestTarget` checks before discovery, schema reads, and execution. Revalidate enabled-window ownership immediately before dispatch. Bind each opaque tool reference to the selected extension connection, agent session as appropriate, tab, document identity, origin, and catalog revision. References must not route themselves to another profile or to a replacement document. Include frame identity when frame support is added. [Existing routing constraints](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-page.js#L168-L260); [Profile ambiguity checks](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/native-host/src/daemon.js#L1281-L1383)
- Retain descriptors in the isolated content-script context under a per-document nonce and bounded TTL. Refresh discovery before execution; reject changed, removed, or replaced registrations. Use `toolchange` to invalidate catalog references, and invalidate on full navigation, document replacement, extension reconnect/reload, tab close, window move, access disable, or content-script reinjection. SPA navigation can change tools without replacing the document, so a URL comparison alone is insufficient. Revalidation is not a guarantee of atomicity; propagate browser stale-descriptor errors instead of re-resolving a replacement tool by name. [WebMCP toolchange](https://developer.chrome.com/docs/ai/webmcp/imperative-api); [Existing frame/document-ref pattern](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-content-script.js#L249-L265); [Window lifecycle](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-window-session.js)
- Treat execution as mutating, sensitive, sequential, and non-retryable by default, even with `readOnlyHint:true`. Only the metadata list/schema methods should join safe batch/retry allowlists. A timeout, navigation, disconnect, or closed response port after dispatch means the action may have happened. Preserve that uncertainty; never advise re-execution merely to get a larger result. Browser transport failure is not proof of transaction rollback. [Current safe allowlists](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/protocol/src/registry.js#L843-L905); [Current retry allowlist](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/handlers-utils.js#L196-L251); [Official confirmation guidance](https://developer.chrome.com/docs/agents/security)
- Use AbortController for the local page execution timeout and pass its signal to the browser API. Distinguish abort requested from work stopped. An executed callback may ignore the signal or have already committed effects. Do not claim existing MCP request cancellation propagates to WebMCP; an end-to-end cancel protocol or execution-ID cancellation method would be additional work. [WebMCP cancellation](https://developer.chrome.com/docs/ai/webmcp/imperative-api); [Existing MCP cancellation boundary](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/handlers-utils.js#L100-L164)
- Validate the wire envelope and JSON serializability, cap argument bytes, schema bytes/depth, catalog entries, descriptions, execution duration, and returned data. Let the browser apply its tool input validation; if BBX adds JSON Schema validation, do not claim unsupported schema dialects are enforced. Do not fetch external `$ref` URLs or execute tool descriptions. Treat schemas, names, descriptions, annotations, and results as untrusted site data regardless of the hint. [Official schema and API](https://developer.chrome.com/docs/ai/webmcp/imperative-api); [Agent security](https://developer.chrome.com/docs/agents/security)
- Preserve complete schemas and structured results within declared limits. On overflow, return an explicit rejected/limited payload with execution status preserved, or retain the already-produced output behind a bounded result reference for subsequent read-only retrieval. Do not apply the current generic recursive truncator or generic MCP object-depth truncator unchanged to authoritative schema/result JSON. The first release can reject oversized results instead of adding artifact storage, but must report that the action ran. [Current truncator](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-helpers.js#L348-L447); [MCP truncator](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/handlers-utils.js#L478-L530); [Official response rejection guidance](https://developer.chrome.com/docs/agents/security#set_token_limits)
- Keep top-document-only scope in the first release. Defer automatic iframe enumeration, remote-origin aggregation, and destination-document JSON-LD extraction. When adding frames, preserve origin/frame/document identity, enforce an explicit origin policy, respect browser `tools` delegation/exposure, and do not adopt the example's page-visible `postMessage` frame-ID discovery as a security boundary. Existing DOM iframe support does not prove correct WebMCP authorization. [Official iframe rules](https://developer.chrome.com/docs/ai/webmcp/imperative-api); [Example frame messaging](https://github.com/GoogleChromeLabs/webmcp-extension/blob/main/extension/content.ts); [BBX frame helper](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-content-script.js#L200-L289)
- Do not turn browser API navigation `null` into an empty successful transaction result. Report the navigation indication and verify via existing `page.get_state` or `page.wait_for_load_state`; ordinary page-state inspection is a safe fallback. Do not automatically scrape every JSON-LD block in a new tab as the tool's trusted result. [Documented navigation behavior](https://developer.chrome.com/docs/ai/webmcp/imperative-api); [Current page-state/wait methods](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-page.js)
- Enabled-window consent is necessary but does not authorize purchases, sends, deletes, or data exfiltration. For development MVP, state clearly that the invoking agent must enforce user authorization and limit use to trusted test pages. For a general-user release, add deterministic action-level confirmation as a deliberate separate policy change, with approval bound to exact tool/document/arguments. Never treat a caller-supplied boolean or `readOnlyHint` as proof of user consent. Audit only tool identity, origin, status, duration, and bounded counts; redact arguments, outputs, and schema examples from persisted logs. [Official agent consent guidance](https://developer.chrome.com/docs/agents/security); [Existing sensitive-log precedent](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-action-log.js#L322-L428)

### Gaps

- Exact browser guarantees about retaining a descriptor across tool unregister/re-register need a live compatibility test. BBX must not advertise atomic stale-check guarantees it has not established.
- Production confirmation UX, trusted-origin policy, argument-level privacy policy, schema dialect coverage, and end-to-end cancellation need explicit design decisions. The minimal transport adapter cannot solve them merely by copying annotations.
- I did not estimate implementation time or token savings. There is no measured BBX/WebMCP benchmark in this research, so any efficiency claim should remain qualitative until tested.
