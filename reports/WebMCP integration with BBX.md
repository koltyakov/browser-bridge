# Use WebMCP alongside BBX, not instead

**Yes. WebMCP can complement BBX as an optional way to discover and invoke website-provided tools.** Keep BBX's existing MCP connection and browser automation; add a browser-side adapter behind its generic dispatcher. Current Chrome documentation and an upstream extension demonstrate the required access pattern, but nobody tested it against BBX during this research. The recommendation is **medium-priority, opt-in experimentation**, after core routing and reliability work, rather than default-on production support. Browser availability remains experimental, consequential actions need independent approval, and token savings remain unmeasured. This assessment synthesizes the supplied research as of **October 9, 2026**, with BBX source reviewed at commit `08ace5826301fcdf59ea57b042f85aca930de036`, version 1.12.2. No implementation or live browser benchmark accompanies it. ([Chrome overview](https://developer.chrome.com/docs/ai/webmcp); [extension example](https://github.com/GoogleChromeLabs/webmcp-extension/))

## WebMCP exposes page actions, not an MCP server

WebMCP lets a website describe callable application functions using names, descriptions, input schemas, and JavaScript callbacks. Those callbacks run in the page and can reuse application state and update the visible UI. MCP is the separate agent/server protocol BBX already uses. The WebMCP draft does not prescribe an agent-facing transport, create a network MCP endpoint, or require publishing site tools through MCP `tools/list`. BBX can carry their descriptions and results through its existing MCP server without replacing it. ([Proposal](https://github.com/webmachinelearning/webmcp); [agent integration](https://webmachinelearning.github.io/webmcp/#interaction-with-agents))

The current API is **`document.modelContext`**, with asynchronous `registerTool`, `getTools`, and `executeTool`. Older `navigator.modelContext` and `navigator.modelContextTesting` examples are historical or library-specific, not the current contract. Consumers discover `RegisteredTool` descriptors, then pass a descriptor and a JSON-serializable input object to `executeTool`; stringified arguments are deprecated in Chrome's documentation from version 155. Descriptors contain an owning `Window`, which cannot cross BBX's JSON transport. Keep it in the browser context and serialize only metadata. ([Current draft API](https://webmachinelearning.github.io/webmcp/#api); [Chrome imperative API](https://developer.chrome.com/docs/ai/webmcp/imperative-api))

Version differences matter. Draft IDL makes `inputSchema` optional and returns `Promise<DOMString>` from execution; Chrome prose describes a required schema and a `null` result when navigation occurs. Chrome also implements declarative forms using `toolname` and `tooldescription`, with manual submission by default and optional `toolautosubmit`. That declarative work is **not part of the current community specification**. Treat these as contracts to verify on a target build, not interchangeable guarantees. ([Draft](https://webmachinelearning.github.io/webmcp/); [declarative documentation](https://developer.chrome.com/docs/ai/webmcp/declarative-api); [proposal status](https://github.com/webmachinelearning/webmcp#future-exploration-declarative-api))

## Documented support is experimental and version-sensitive

The October 9 specification is a Draft Community Group Report, explicitly neither a W3C Standard nor on the Standards Track. Chrome's October 7 overview still labels WebMCP an origin trial, beginning with Chrome 149, and documents the local testing flag. The project reports Edge origin-trial support from version 150. **Unconditional default-on shipping was not established.** Chrome Status records a September request to extend the trial through milestone 162, but a request and rollout planning fields are not release confirmation. ([Specification status](https://webmachinelearning.github.io/webmcp/); [Chrome overview](https://developer.chrome.com/docs/ai/webmcp); [implementation status](https://raw.githubusercontent.com/webmachinelearning/webmcp/main/implementation-status.md); [Chrome Status](https://chromestatus.com/api/v0/features/5117755740913664))

Mozilla's recorded position is neutral; WebKit's is opposed. Neither supplies an interoperable browser baseline. BBX currently supports Chrome 114+, so WebMCP cannot become a prerequisite for ordinary operation. Detect availability in the selected document, distinguish unavailable API from an empty catalog, and label polyfill or legacy support separately. Checking a property alone does not prove native implementation. No research established support on the user's installed build, precise legacy compatibility, or origin-trial extension approval. Mutable upstream URLs describe what researchers retrieved on the cutoff date. ([Mozilla](https://github.com/mozilla/standards-positions/issues/1412); [WebKit](https://github.com/WebKit/standards-positions/issues/670); [BBX manifest](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/manifest.json); [independent library example](https://github.com/WebMCP-org/chrome-devtools-quickstart))

## BBX already transports calls; a scoped adapter is new work

BBX has profile/window routing, native messaging, content-script injection, MAIN-world execution, CDP evaluation, and generic `browser_call` dispatch. It has **no existing `webmcp.*` family**, descriptor registry, stale-tool handling, or action-level WebMCP approval policy. Its closed method registry rejects unknown methods. Existing `page.evaluate` can support a development experiment, but that is not first-class WebMCP support. ([BBX architecture](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/AGENTS.md); [registry](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/protocol/src/registry.js); [evaluation implementation](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-evaluate.js))

Prefer a direct content-script adapter. Chrome explicitly supports extension consumption, and Google's example calls `document.modelContext.getTools()` and `executeTool()` there. An experimental CDP `WebMCP` domain is an alternative, not the smallest route. It discovers tools through `toolsAdded` events after `enable`, not a `listTools` command. `invokeTool` returns an invocation ID; completion arrives later through `toolResponded`. Its availability on the user's browser was not tested. ([Extension source](https://raw.githubusercontent.com/GoogleChromeLabs/webmcp-extension/main/extension/content.ts); [CDP definition](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/WebMCP.pdl))

Three **proposed, unshipped** methods fit BBX's existing generic design. `webmcp.list_tools` returns bounded summaries, support/backend state, document identity, catalog revision, and opaque `toolRef` values. `webmcp.get_tool` returns one complete input schema, or an explicit size error. `webmcp.execute_tool` accepts that reference, object arguments, deadline, and required approval, then reports result, navigation, error, or uncertain outcome. Site tools remain untrusted data in these responses, not dynamically registered top-level MCP tools. Initial scope should be top-document only, explicitly filtering `tool.window === window` because default discovery also includes same-origin frames. ([Discovery semantics](https://developer.chrome.com/docs/ai/webmcp/imperative-api); [BBX static tool policy](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/toolset.js))

The concrete integration plan is below. Every edit is a recommendation, not a change made by this report.

| Area | Recommended files and responsibility |
| --- | --- |
| Protocol | `packages/protocol/src/types.ts`, `registry.js`, `protocol.js`, `defaults.js`, and `budget-presets.js`: typed methods, validation, deadlines, discovery budgets, and execution classification. Add error definitions if needed. |
| Extension | New `packages/extension/src/content-webmcp.js` and `background-webmcp.js`; wire through `background-content-script.js`, `content-script.js`, and `background.js`. Retain descriptors, feature-detect, enforce scope, execute, and abort locally. Keep content scripts classic JavaScript with JSDoc. |
| Lifecycle and output | `packages/extension/src/background-window-session.js`, `background-helpers.js`, and `background-action-log.js`: invalidate references, preserve atomic JSON, and redact logs. |
| MCP evidence | `packages/protocol/src/summary.js`, `packages/mcp-server/src/handlers-utils.js`, and `handlers-page.js`: preserve schemas/results and prohibit execution retries. |
| Agent guidance | `skills/browser-bridge/SKILL.md`, its protocol/interaction/token-efficiency references, and `packages/mcp-server/src/guidance.js`: optional availability, approvals, failure handling, and fallback. |

No new native-host transport, MCP server, host permissions, or website-specific CLI commands are needed for the initial adapter. Existing response truncators need method-aware exceptions because recursively shortening a schema or structured result can change its meaning. ([Generic handler and atomic-output precedent](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/handlers-page.js#L508-L599); [budget implementation](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-helpers.js#L348-L447))

## Authentication persists; approvals and failure policy must be explicit

Page callbacks reuse the user's authenticated session. BBX should neither export cookies nor create another credential flow; server authorization remains the site's responsibility. But window access is not permission to purchase, send, delete, or disclose private data. Separate bridge access, authorization for the exact action, and any site-required human confirmation. For development, restrict use to approved test pages and agent-enforced authorization. A general-user release needs deterministic approval bound to profile, tab/document, origin, tool version, and exact arguments. A caller boolean is not proof of consent, and native portable confirmation cannot be assumed from the current draft. ([Agent security](https://developer.chrome.com/docs/agents/security); [tool security](https://developer.chrome.com/docs/ai/webmcp/secure-tools); [open questions](https://github.com/webmachinelearning/webmcp#open-questions))

Treat descriptions, schemas, annotation hints, and outputs as untrusted. `readOnlyHint` neither proves safety nor makes execution batch-safe. Enforce origin and payload limits, avoid external schema-reference fetching, and redact arguments/results from persisted audit logs. Bind references to document and connection identity; invalidate on `toolchange`, navigation, reconnect, access revocation, and teardown. Reject removed or replaced tools instead of choosing a new registration by name. Revalidation reduces races but does not establish atomicity. Cross-origin frames should wait until explicit policy delegation, exposure, and discovery rules are tested. ([Draft security](https://webmachinelearning.github.io/webmcp/#security-privacy); [registration race](https://webmachinelearning.github.io/webmcp/#unregistration-execution-race); [iframe rules](https://developer.chrome.com/docs/ai/webmcp/imperative-api#cross-origin_iframes))

**Execution must be sequential and non-retryable by default.** A timeout, disconnect, navigation, or oversized result can follow a committed action. Report that uncertainty and inspect postconditions before considering another action. Request cancellation with an `AbortSignal`, but do not claim rollback; existing MCP cancellation does not prove page-level cancellation. Preserve complete bounded schemas/results or reject them explicitly, retaining whether execution occurred. DOM fallback is safe for missing tools before dispatch, not for automatically repeating an uncertain mutation. ([Cancellation API](https://developer.chrome.com/docs/ai/webmcp/imperative-api); [BBX retry/cancellation boundaries](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/mcp-server/src/handlers-utils.js))

## A small proof of concept should decide further investment

The smallest experiment requires no BBX source changes. On an explicitly approved experimental Chrome profile/tab and controlled demo, use existing `page.evaluate` to feature-detect, discover bounded top-document metadata, then resolve and execute one harmless tool within the browser context. JSON-encode arguments as data, never interpolate page-provided code. Independently verify the visible result with BBX DOM reads. Do not automatically enable flags, install polyfills, or infer approval from discovery. Native versus library-provided behavior needs explicit verification. ([Existing evaluator](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/packages/extension/src/background-evaluate.js); [demo collection](https://github.com/GoogleChromeLabs/webmcp-tools))

Promotion to the typed adapter should require these acceptance gates, implemented with a deterministic fixture under `tests/fixtures/browser-reliability/`, new `content-webmcp.test.ts` and `background-webmcp.test.ts` under `packages/extension/test/`, and a live test under `packages/integration-tests/`.

| Gate | Required result |
| --- | --- |
| Availability and scope | Absent API differs from empty catalog; normal BBX reads still work. Wrong profile/window/document and stale references fail closed; duplicate frame names cannot misroute. |
| Actions and approvals | An imperative simulated action matches a DOM-verified result. Denial prevents callback execution regardless of hints. Declarative prefill leaves manual submission pending. |
| Failure safety | Timeout, rejection, abort, navigation, and oversized output have distinct outcomes; no automatic replay or duplicate DOM fallback occurs. |
| Data and trust | Full schemas remain intact or fail explicitly. Malicious metadata/results cannot expand deterministic permissions; audits do not persist sensitive payloads. |
| Incremental value | Compare identical tasks against BBX structured DOM/input, including discovery costs, tokens, calls, latency, and success rate. |

These are proposed tests, not observed results. A reasonable project-defined value gate is at least 20 repeated multi-step tasks, no lower success rate, and at least 25% fewer model-visible tokens or bridge calls. That threshold is a decision criterion, not a published finding. Future implementation also requires repository lint, typecheck, tests, and a live CLI-to-Chrome flow. ([BBX validation rules](https://github.com/koltyakov/browser-bridge/blob/08ace5826301fcdf59ea57b042f85aca930de036/AGENTS.md))

## Conclusion

Fund the bounded experiment before committing to production support. WebMCP earns higher priority when BBX users repeatedly automate cooperating applications and measured savings justify the approval and lifecycle work. For arbitrary-site inspection and CSS debugging, existing BBX methods remain the better investment. A successful prototype would establish one additional execution option, not justify replacing the bridge or trusting site-authored tool claims.
