# Agent setup and detection fingerprints

**Status: managed MCP setup, CLI skills, and passive installation detection are implemented. MCP active-caller attribution remains separate future work.**

Checked **2026-10-22**. Gemini CLI, Cline, Zed's native agent, Amp, and Factory Droid all have verified local stdio MCP configuration and discoverable `SKILL.md` workflows. BBX uses the stable keys `gemini`, `cline`, `zed`, `amp`, and `droid`, after Antigravity and before Generic agents, without reordering existing targets. It registers the globally installed executable as **`command: "bbx"`, `args: ["mcp", "serve"]`**. Agent installation, BBX installation, MCP registration, and CLI-skill installation are separate. Installation evidence, retained configuration, and active-caller hints also remain separate. Automated fixtures cover these integrations, but none was tested end to end inside the five agents. The companion [evidence catalog](./agent-fingerprints.json) records sources, confidence, scope limits, implementation status, and the original research baseline as inert data.

## Registry and seven additional targets

The ordered [native registry](../internal/bridge/agents_registry.go) now owns all 20 supported targets, including existing agents. Each entry declares labels, aliases, MCP scopes and format, config paths, skill paths, transport validation, and presence evidence or a detection hook. Shared installers consume those definitions. Client-specific path and detection functions remain separate, registered hooks rather than additional target switches. The extension uses the ordered setup response instead of maintaining another agent list. Existing agents retain their prior directory/PATH detection hints; moving them into the registry does not upgrade those hints into verified identity.

The seven additions follow Factory Droid in this order: `pi`, `kilo`, `qwen`, `goose`, `openhands`, `muse`, `grok`. Generic `agents` remains last. These contracts were checked against official documentation and source on 2026-10-22, not tested inside the clients. No agent software was installed or personal agent settings changed during implementation.

## Each agent has a distinct installation contract

### Gemini CLI needs its own target, separate from Antigravity

Install the **agent** with `npm install -g @google/gemini-cli`; its executable is `gemini`. Official alternatives are `brew install gemini-cli` on macOS/Linux and `sudo port install gemini-cli` on macOS. Node 20+ is documented. Recommended OS versions are macOS 15+, Windows 11 24H2+, and Ubuntu 20.04+; do not turn recommendations into an exhaustive support boundary. Ephemeral `npx @google/gemini-cli` launches are supported, so absent global installation does not exclude an active client. Google's current transition banner distinguishes Gemini CLI from Antigravity CLI. It does not justify reusing BBX's existing Antigravity config path or identifying the host from a Gemini model name. ([Installation](https://geminicli.com/docs/get-started/installation/), [package identity](https://github.com/google-gemini/gemini-cli/blob/a713410aba5d594594e20d5c822e3aab8f822089/packages/cli/package.json))

For **BBX MCP registration**, documented syntax composes to `gemini mcp add --scope user --transport stdio browser-bridge bbx mcp serve` or `--scope project`. The default scope is project. Prefer BBX's targeted file editor for upgrades because Gemini's add implementation replaces a same-name entry. `GEMINI_CLI_HOME=/custom/root` means `/custom/root/.gemini/settings.json`, not `/custom/root/settings.json`; it also redirects the user `.agents` skill root. Settings permit comments, but the parser does not establish arbitrary JSON5 support. File precedence is defaults < system defaults < user < project < system policy. Verified administrator paths are `/Library/Application Support/GeminiCli/settings.json`, `/etc/gemini-cli/settings.json`, and `C:\ProgramData\gemini-cli\settings.json`, with `GEMINI_CLI_SYSTEM_SETTINGS_PATH` and independent `GEMINI_CLI_SYSTEM_DEFAULTS_PATH` overrides. They are not BBX install targets. ([Add command](https://geminicli.com/docs/tools/mcp-server/#adding-a-server-gemini-mcp-add), [home resolver](https://github.com/google-gemini/gemini-cli/blob/a713410aba5d594594e20d5c822e3aab8f822089/packages/core/src/utils/paths.ts#L17-L28), [settings precedence](https://github.com/google-gemini/gemini-cli/blob/a713410aba5d594594e20d5c822e3aab8f822089/docs/reference/configuration.md#L7-L76), [admin paths](https://github.com/google-gemini/gemini-cli/blob/a713410aba5d594594e20d5c822e3aab8f822089/packages/cli/src/config/settings.ts#L106-L126))

For the **BBX CLI skill**, copy the existing bundle to the native `.gemini/skills/browser-bridge` destination. Gemini's own `gemini skills install <directory-or-git-url> --scope user` uses user scope by default; project skills use `--scope workspace`, not MCP's `project`. Matching frontmatter names resolve built-in < extension < user `.gemini` < user `.agents` < workspace `.gemini` < workspace `.agents`. `/skills reload` rescans skills. Untrusted folders skip project skills and settings, and current source blocks all stdio MCP there, even globally registered servers. Current trust source defaults to enabled despite conflicting guide prose. Do not set `trust:true` or skip-trust overrides. After external settings edits, start a fresh Gemini session, inspect `/mcp` or `gemini mcp list`, then validate skill activation separately. Sanitized subprocess environments and sandboxes still require a BBX connectivity test. ([Skills](https://geminicli.com/docs/cli/skills/), [stable precedence](https://github.com/google-gemini/gemini-cli/blob/6006c14a4decfe4b891c6263ad6ad5992e404b5b/packages/core/src/skills/skillManager.ts#L54-L99), [stdio trust guard](https://github.com/google-gemini/gemini-cli/blob/a713410aba5d594594e20d5c822e3aab8f822089/packages/core/src/tools/mcp-client.ts#L2382-L2431), [trust default](https://github.com/google-gemini/gemini-cli/blob/a713410aba5d594594e20d5c822e3aab8f822089/packages/cli/src/config/trustedFolders.ts#L32-L36))

### Amp uses a literal dotted key and executor-local setup

## Detection must separate installs, history, and callers

Use three independent evidence categories plus readiness. **Installation** requires a real executable/app/extension with corroborated identity. **Historical/configured** evidence includes directories, old package receipts, legacy extension files, and BBX registration labels, none of which proves a running client. **Active caller** means metadata observed on the current connection or verified process context, with its own confidence. A missing global executable does not refute an ephemeral or remote runtime. All MCP `clientInfo`, environment variables, configured labels, and process fingerprints are **spoofable attribution hints, never authorization**. Do not read API keys, auth files, transcripts, whole environments, or keychains for detection. Do not execute catalog strings or regexes. Any future version probe must use an approved, resolved executable, literal argv, timeout, bounded output, and no installation/update fallback.

## Conclusion

Ship verified setup contracts independently from caller recognition. Gemini, Cline, and native Zed provide source-verifiable peer names, but even those names cannot prove installation, selected model, editor host, or permission. Amp and Droid should remain fully configurable targets with **unknown protocol identity** until a controlled observation or authoritative runtime source establishes more. That avoids blocking useful setup on unavailable metadata while keeping attribution honest.

Managed setup now implements standard locations and scope limits without installing agent binaries or altering personal settings during development. Custom runtime profiles, effective-skill/readiness diagnostics, active MCP peer attribution, and live acceptance in the five agents remain separate follow-up work.
